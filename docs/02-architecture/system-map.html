IDEA AUDITION の全体図

いま本番で動いている姿です（Cloud Run の revision 00008、2026-11-08 時点）。審査員はホストが作った部屋のリンク（/a/kqd-rmzw-tbe の形）から入り、画面とサーバーは自作のプロトコル CAMP（Collaborative Agent Mediation Protocol）で WebSocket の上を話します。好みエンジン（ADR-0009）と聞き間違いの補正（ADR-0011）も入っています。

会場（審査員のPC） Cloud Run のコンテナ Google Cloud のサービス Vertex AI（Gemini） 開発・チーム

サービス構成図 01 / SERVICE MAP

どのツールがどのツールと、何でつながっているか。実線は毎回のやり取り、点線は毎回ではないつながり（権限・請求・端末内の処理・完成時の公開）です。線の色と太さはすべて同じにし、意味は実線と点線だけで分けています。

コンテナは1つ画面の配信、部屋の発行、/camp、/voice、SessionActor が同じ Cloud Run の1台に入っています。最大1台・セッションアフィニティ（同じ人を同じ台につなぐ設定）で、全員が同じメモリ上の部屋に入ります。
Gemini を呼ぶのはサーバーだけブラウザは鍵もトークンも持ちません。サービスアカウント idea-audition-run の権限で Vertex AI と Firestore を呼びます。
合言葉は使わない部屋の ID（26の10乗通り）を知っている人だけが入れます。部屋を作るのは送り手ごとに1時間10回、同時に20部屋までに絞り、Gemini のクレジットを守ります。Secret Manager はもう使っていません。

好みの更新taste ← taste·0.5^(Δt/90秒) ＋ 重み·案の8軸。決勝へのドラッグは強く、却下はマイナス、迷いは弱く効きます。
選抜案を多めに作り置きし、好みとの近さ（fit）・2人の間（bridge = min(fitA, fitB)）・目新しさで点をつけ、MMR（すでに出た案に似た候補を減点する選び方）で似た案を外し、温度つきで抽選します。好みに寄せる枠は5枠中2枠まで、決勝の案とほぼ同じ案はどの枠でも出しません。
落ちたときGemini が失敗したら固定データで続行。埋め込みが失敗したら 8軸だけでスコアをつけます。

部屋を作って参加する 05 / ROOMS

Google Meet と同じく、ホストが部屋を作ると推測されにくいリンクができ、そのリンクを開いた人が同じ部屋に入ります。作られていない部屋や片付けられた部屋のリンクは「見つかりません」になり、再接続はしません。

sequenceDiagram
  autonumber
  participant H as ホストのブラウザ
  participant B as 参加者のブラウザ
  participant R as Cloud Run
  participant A as SessionActor
  participant F as Firestore
  H->>R: POST /api/rooms
  R->>R: 回数の上限を確認（送り手ごとに1時間10回・同時に20部屋）
  R->>A: 部屋を作る（ID の例 kqd-rmzw-tbe）
  A->>F: sessions/{id} をすぐ保存
  R-->>H: 201 roomId（画面は /a/{id} に移る）
  H->>B: 招待（リンクのコピー・共有シート）
  B->>R: WebSocket /camp ＋ hello（部屋 ID）
  alt 部屋がない
    R-->>B: protocol_error ROOM_NOT_FOUND ＋ 終了コード 4404
  else 部屋がある
    opt メモリに部屋が無い（再起動のあと）
      A->>F: sessions/{id} を読んで復元
    end
    A-->>B: welcome（参加者 ID・snapshot）
    A-->>H: JUDGE_JOINED を全員へ（4人まで審査員、5人目からは観覧）
  end

声・言及・迷い 07 / VOICE

音声は gemini-3.5-transcribe-live で文字にし、1.2秒の無音で1発言にまとめます。部屋の語彙（キャラ名・企画名・論点）で聞き間違いを直し、言葉にならない迷いも拾って、見ているキャラに反応させます。

  participant A as SessionActor

  participant G as gemini-3.5-flash

  V->>L: 音声を中継
  L-->>V: 途中の文字・確定した文字

  A->>A: 聞き間違いの補正 → 名前の言及 → 退場を取り消し / 却下
  A->>A: 合意台帳：主張と賛否を更新
  A-->>M: JUDGE_UTTERANCE_RECEIVED・CONSENSUS_UPDATED

  G-->>A: 別案
  A-->>M: CANDIDATE_REVISED

CAMP メッセージ 10 / PROTOCOL v1

封筒・順序・重複排除・再接続は @camp-protocol/kit（packages/camp）が受け持ち、IDEA AUDITION の語彙は packages/protocol の Zod スキーマで検証します。Command と Event は Firestore に残り、Ephemeral（カーソルなど）は残しません。

種類向きメッセージ役割
hello / welcome双方向hello · welcome部屋への参加と、現在の snapshot
Commandブラウザ → サーバーSTART_AUDITION · SET_AI_MODE · REQUEST_PROMOTION · NEXT_IDEA · REJECT_CANDIDATE · PIN_CLAIM · UNPIN_CLAIM · ASK_CANDIDATE · REQUEST_REFINEMENT · SUBMIT_UTTERANCE · START_CHAMPION_VOTE · CAST_VOTE · CLOSE_VOTE · RESOLVE_TIE · SELECT_CHAMPION · RESET_SESSION · REGENERATE_PROPOSAL状態を変える頼みごと。result で成否が返る
Signalブラウザ → サーバーSOFT_SIGNAL迷い・沈黙・笑い・声量と、そのとき見ていたカード。返事なし・1人毎秒2件まで（ADR-0010）
protocol_errorサーバー → ブラウザUNSUPPORTED_VERSION · MALFORMED · UNKNOWN_TYPE · NOT_JOINED · RATE_LIMITED · ROOM_NOT_FOUND黙って捨てずに、相手が直せる情報を返す
Eventサーバー → 全員SESSION_STARTED · SESSION_RESET · JUDGE_JOINED · JUDGE_LEFT · HOST_CHANGED · CANDIDATE_SPAWNED · CANDIDATE_ARCHIVED · CANDIDATE_LEAVING · CANDIDATE_STAYED · CONSENSUS_UPDATED · PROPOSAL_UPDATED · AI_MODE_CHANGED · PROMOTION_CONFIRMED · FINALIST_REFINEMENT_STARTED · FINALIST_CRITIQUE_POSTED · FINALIST_VERSION_PUBLISHED · CANDIDATE_ANSWERED · JUDGE_UTTERANCE_RECEIVED · CHAMPION_VOTE_STARTED · VOTE_CAST · TIE_DETECTED · CHAMPION_SELECTED起きたこと＋snapshot 全体。画面は snapshot を置き換えるだけ
Eventサーバー → 全員TASTE_UPDATED · CANDIDATE_REACTED · CANDIDATE_REVISED好みレーダーの更新、🤔 の反応、別案への差し替え
Ephemeralブラウザ → 他の人CURSOR_MOVED · DRAG_PREVIEW · FOCUS_CHANGED · MIC_STATE_CHANGED · THEME_DRAFT保存しない一時的な共有。FOCUS_CHANGED は迷いの宛先探し、THEME_DRAFT はロビーでホストの入力をほかの人に映すのに使う

CAMP とOSSへの道 15 / PROTOCOL & OSS

CAMP は TCP や WebSocket の仲間ではなく、その上に載るアプリケーション層のプロトコルです。WebSocket は「届ける」だけで、4人が同時に昇格したら誰が勝つか、返事の前に切れた操作をどうするか、遅れて返った AI の結果をどう扱うかは決めてくれません。そこを決めているのが CAMP です（ADR-0010、docs/protocol/camp-v1.md）。

flowchart TB
  APP["IDEA AUDITION の語彙<br/>REQUEST_PROMOTION · CANDIDATE_SPAWNED · SOFT_SIGNAL …"]
  CAMP["CAMP v1（自作）<br/>直列処理と seq · 重複排除 · 再接続 · 古い AI 結果を捨てる · 部屋"]
  WS["WebSocket（RFC 6455）<br/>双方向・メッセージ単位で届ける"]
  TLS["TLS（暗号化）"]
  TCP["TCP<br/>順番どおり確実に届ける"]
  IP["IP"]
  APP --> CAMP --> WS --> TLS --> TCP --> IP
プロトコルとして決めることCAMP v1 の答え
送れるメッセージhello・welcome・command・result・event・ephemeral・signal・protocol_error
誰が入れるかアプリが作った部屋だけ。ない部屋は ROOM_NOT_FOUND（終了コード 4404）
処理の順序部屋ごとに1件ずつ。Event に欠番なしの seq と snapshot 全体
同時操作の衝突状態の前提条件で判定。対象の版は expected.rev → STALE_VERSION
二重処理と再接続commandId ごとに結果を覚えて同じ result を返す。再接続したら同じ ID で送り直す
AI の遅れた結果部屋を作り直す前に始まった結果は捨てる（epoch）
バージョン・壊れたメッセージ・送りすぎprotocol_error で理由を返し、決まった終了コードで閉じる
いまの状態@camp-protocol/kit として実装し、適合テストと仕様書（SPEC.md）をそろえた。GitHub の camp-protocol/camp と npm の @camp-protocol は確保済み。完成したら英語の履歴で公開し直し、npm に出す。
アプリとの関係IDEA AUDITION は同じリポジトリの packages/camp を読んでいる。npm に出したら、読み込み先を npm の版に切り替える（import はそのまま）。
アプリの言葉を持たないCAMP の中にアプリの語彙が混ざらないことを、境界テストで毎回確かめている。
