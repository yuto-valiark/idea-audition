# ChatGPT に渡す：発表とスライドの構成を一緒に考えるためのプロンプト

- 作成：2026-11-09
- 使い方：下の「ここから」〜「ここまで」を、そのまま ChatGPT に貼る
- 中身：運営のキックオフ資料・提出ルール・ドキュメントのテンプレート、チームの決定事項、プロダクトの事実（リポジトリの設計資料と実装から）を、重み付けせずに並べたもの
- ChatGPT は企画の相談相手として使う。運営のルールにより、スライドやデモで他社の AI 製品を前面に出すことはしない

ここから

---

あなたは、学生ハッカソンのピッチ（発表）とスライド構成を一緒に考えるパートナーです。以下に、私たちが持っている一次情報を**重み付けせずに**すべて並べます。どれが大事かは決めつけず、すべてを材料として使ってください。足りない情報や、判断にチームの決定が必要な点があれば、推測で埋めずに質問してください。

## 0. お願いしたいこと

1. 発表全体の構成案を **2〜3通り** 出し、それぞれの良い点・弱い点を比べてください（大会のテーマが「AI の提案を鵜呑みにせず、比べて理由を持って選ぶ」なので、私たちも比べて選びたい）
2. 各案について、スライド1枚ごとの「タイトル・載せる内容・話す内容の要点・想定時間」を出してください
3. 各スライドが、下の審査基準（8項目・24点）のどれに答えているかを対応させてください。8項目すべてに答えているかを最後に点検してください
4. 冒頭の「つかみ」の台詞案を何通りか出してください
5. 審査員から来そうな質問と、その答え方の案を出してください
6. デモの見せ方（動画と実演の分け方、止まったときの切り替え）の案を出してください
7. 持ち時間がまだ分からないので、**5分版**を基本にし、短縮版（3分）と延長版（7分）にするなら何を削る・足すかも示してください

守ってほしいこと：
- **架空の数字は作らない**。数字は下に書いた事実か、「ここに実測値が入る」と枠で示す。実測・試算・小さな予備実験は区別して書く
- スライドやデモで**他社の AI 製品（ChatGPT など）を前面に出さない**（大会のルール）
- 下の「完成した前提」に書いた機能は、発表時点で入っているものとして扱ってよい。ただし、実物と違うことを言わない（デモ動画の偽装は審査対象外になる）
- 日本語で答える

## 3. プロダクトの情報：IDEA AUDITION

### 3-1. ひとことで
- 名前：**IDEA AUDITION**
- キャッチコピー：「AIがプレゼン。あなたが審査員。」「まだ、人間がアイデア出してるの？」「人間に必要なのは、『これ、おもろいかも。』そのセンスだけ。」「ひらめくのはAI。見つけるのは、あなた。」
- 説明：アイデア出しを、オーディションの審査で終わらせる企画決めツール。AI のキャラクターたちが次々にアイデアをプレゼンし、人間（審査員、最大4人）は直感で選び、みんなで磨いて、最高の1案に決める。決まったら企画書（PDF）がすぐ出る
- 本番 URL：https://idea-audition-852280753109.asia-northeast1.run.app （Cloud Run で動作中）

### 3-2. 今の使い方の流れ（実装済み）
1. トップで「オーディションを作る」→ 部屋のリンクができる（Google Meet のようなリンク。合言葉は無い）。リンクのコピーと共有シート（AirDrop・LINE など）で招待
2. 入った人は名前を入れる。審査員は1部屋4人まで、5人目以降は観覧モード
3. ホストがテーマ（例：「大学の学食をもっと楽しくする企画」）を入れ、「みんなで審査」か「ひとりで審査」、AI のモード（Gemini／固定データ＝無料）を選んで開始
4. 下段に AI のキャラクター5体が並び、それぞれ案を持ってプレゼン（企画名・説明・「誰の・困りごと・どう解く」の3行）。注目されない案は入れ替わる
5. 気に入った案を上段（決勝の枠、3つ）に上げる。上がった案は、ほかのキャラとの相互批評と、審査員の指示で改良される
6. 声やテキストでキャラに質問すると、キャラが吹き出しで答える（待つ間は「考え中…」）
7. 決勝の3案から投票で優勝を決める → 企画書（第1部：企画の中身、第2部：審査レポート）が PDF で出る。文章のコピーと共有もできる
- 審査員どうしは通話（声）でつながる。部屋に入ると自動でつながり、マイクのボタンはミュートの切り替えだけ。観覧者も聞くだけで参加できる

### 3-3. 完成した前提で入る機能（Issue に上がっている残りのタスク）
- 音声：聞き取りの精度をモデルや設定を変えて比べて決める ／ 文字起こしを画面に出さない ／ 審査の話題に合う発言だけを残し、まとめてからコメントとして出す（雑談は拾わない）／ 声の調子（温度感）を読んで AI の文脈に入れる
- 審査の流れ：5体並びをやめ、キャラが1人ずつスポットライトの中で登場。1人10〜15秒の制限時間。参加者全員がボタンを押したら決勝に上がる（オーディション番組の審査員ボタンの形）。3人合格するまで繰り返す ／ 1人合格したら、次の枠ではそこまでの会話を AI の文脈に使わない（好みは残す、などを実験で決める）／ 決勝では、選んだ1人だけ前に出して深掘り ／ 改良の履歴を版ごとに見て、前の版に戻せる
- 見た目・動き・音：キャラの反応とアニメーション（表情違いの画像）／ 返事を待つ間のアニメーション ／ 効果音
- 小さなもの：好みの8軸グラフを常に表示 ／ 退出ボタン
- 数字：会議ごとの指標をログから自動で出す ／ 会議に入れたときのメリットの試算 ／ 終わったあとのアンケート（アプリ内）／ 小さな比較実験（ふつうの AI チャット vs IDEA AUDITION）／ CAMP の技術効果の実測
- CAMP の公開リポジトリへの反映と npm 公開

### 3-4. AI のしくみ（実装済み）
- **案の生成**：テーマと審査の文脈から、Gemini が案を作る。構造化出力（決まった形の JSON）で受け取る。3件ずつ並列に作る
- **好みエンジン**：案と審査員の好みを同じ **8つの軸**（コスト・新規性・手軽さ・話題性・継続性・社会性・規模・広さ、それぞれ −1〜+1）で表す。選んだ・話した・見ていた・迷った（「うーん」）から一人一人の好みを読み、次に出す案の方向（好みに寄せる／あえて外す／審査員の間をつなぐ／ワイルドカード）を変える。似すぎた案は埋め込み（gemini-embedding）で判定して除く
- **迷いへの反応**：審査員が迷うと、キャラが「どこが引っかかった？」と聞き、その案の別案を作る
- **合意台帳**：会話から「論点」と、誰が賛成・反対したかを記録し、合意した方針を新しい案・改良・回答・企画書に反映する（人間の発言と操作だけを根拠にする）
- **相互批評による改良**：決勝の案は、ほかのキャラからの批評と審査員の指示で版を重ねて改良される（版はすべて残る）
- **回答**：キャラへの質問に答える。聞き間違いで意味が通らない質問は答えず「もう一度言って」と聞き直す
- **音声**：Gemini Live でリアルタイムに文字起こし。聞き間違いは、会議の中で育つ語彙（キャラ名・企画名・論点）と、いま見ているキャラの情報で直す
- **企画書**：優勝が決まる前（決勝がそろった・投票が始まった時点）から裏で作っておき、優勝が決まったらすぐ出す
- **固定データのモード**：AI を使わずに全機能を試せる（無料・デモの練習用）。Gemini が失敗したときも固定データに切り替わる

### 3-5. 技術とアーキテクチャ（実装済み）
- フロント：React 19 + TypeScript + Vite、Zustand、CSS Modules、Motion
- サーバー：Node.js + TypeScript、WebSocket（ws）
- 通信：独自のアプリケーション層プロトコル **CAMP v1**（下の 3-6）
- 実行基盤：**Cloud Run**（asia-northeast1、1台。画面とサーバーを1つのコンテナから配る）。Cloud Build でイメージを作り、Artifact Registry に置く
- AI：**Gemini（Vertex AI 経由）**。案の生成・改良・批評・回答・合意台帳・企画書に gemini-3.5-flash / gemini-3.8-flash（構造化出力）、文字起こしに Gemini Live（gemini-3.5-transcribe-live、サーバーが中継）、似ている案の判定に gemini-embedding。API キーは持たず、Cloud Run のサービスアカウントで認証
- 保存：**Firestore**（確定したイベントの記録と、最新のセッション状態。サーバーが再起動しても部屋を復元できる）。開発用と本番用でデータベースを分けている
- 声：審査員どうしの通話は WebRTC（ブラウザどうしが直接つながる。声はサーバーを通らない）。つなぐための受け渡しだけ CAMP で送る
- 設計の考え方：
  - **サーバー権威**：部屋ごとに1つの「セッションアクター」が操作を1件ずつ順に処理し、全員に同じ順番で結果を配る。画面は判定をせず、サーバーの状態の写しを表示する
  - **差し替え口（ポート）**：AI（Gemini／固定データ）や保存先（Firestore／メモリ）を差し替えられる
  - 部屋の作成は1つの IP から1時間10部屋まで、同時に開ける部屋は20まで（使われない部屋は30分で閉じる）
- テスト：約150件（CAMP 16、通信の型 4、画面 5、サーバー 129）
- 設計の判断は ADR（設計判断の記録）11本に、比べた案・選んだ理由・捨てた案とともに残している：描画方式（DOM/CSS/SVG）、リポジトリ構成（縮小モノレポ）、サーバー権威、CAMP の最小仕様、Gemini の非同期オーケストレーション、下段の入れ替え（注目度）、合意台帳、企画書 PDF、好みエンジン、CAMP のプロトコル化と OSS、音声の聞き間違いの補正

### 3-6. 独自プロトコル CAMP と OSS 公開
- 名前：**CAMP — Collaborative Agent Mediation Protocol**（人も AI も同じ場に集まり、全員が同じ順番で同じ状態を見て、誰の意図を通すかをサーバーが調停する）。英語の説明："A shared decision layer for humans and AI agents."
- なぜ作ったか：何人もの人が同時に操作し、その間に遅い AI の結果が届く場では、「誰が先か」「操作が通ったか」「二度押し・再送」「切断と再接続」「古い AI の結果」「どの版を見て操作したか」を毎回アプリで書くことになり、少しずつ違う形で壊れる。WebSocket はバイトを届けるだけなので、そのルールを一度だけ仕様として書いた
- CAMP がすること：
  - 部屋ごとにサーバーが1件ずつ処理し、変更に通し番号（seq）を付けて全員に同じ順で配る
  - すべての操作に結果（ok か理由コード）を返す
  - 操作 ID で二度押し・再送を1回にまとめる
  - 切断したら同じ参加者として戻り、全体の状態を受け取り、結果の来ていない操作を送り直す
  - AI の処理中に部屋がリセットされたら、古い結果を捨てる
  - 操作に「見ていた版」を付けられ、古い版の操作は断れる
  - 部屋はアプリが作り、リンクで入る（知らない部屋は ROOM_NOT_FOUND）
  - カーソルなど保存しないもの（Ephemeral）と、返事の要らない合図（Signal）
  - 壊れたメッセージ・違うバージョン・送りすぎには、理由つきのエラーと決まった終了コード
- メッセージの種類：hello / welcome / command / result / event（通し番号と状態の写しつき）/ ephemeral / signal / protocol_error
- 実装：TypeScript のパッケージ `@camp-protocol/kit`（サーバーとクライアント。ブラウザでも動く）。IDEA AUDITION の言葉を含まないことをテストで保証している。投票アプリの例（quick-vote）つき
- 公開：仕様書（英語の SPEC.md）・README（英語と日本語）・適合テスト・MIT ライセンス・正方形のロゴ。GitHub の組織 `camp-protocol` と npm の組織 `@camp-protocol` を取得し、公開リポジトリ `camp-protocol/camp` を作成済み。CI は Node 20/22/24 で型チェック・テスト・パッケージの読み込みを確かめる。**npm への公開と公開リポジトリへの最新版の反映は、完成時にまとめて行う予定**（完成した前提では公開済み）
- 名前の経緯：最初は HIP（Human Intent Protocol）と呼んでいたが、Host Identity Protocol（RFC 7401）などと重なり npm の名前も取られていたため、CAMP に改名した
- 測る予定の技術効果：同時操作（4・8・16人が同じ枠に1000回）での食い違い、接続を切りながら送った操作がちょうど1回だけ反映される割合、AI の処理中の取り消しで古い結果が入らない割合、全員に届くまでの時間（中央値・p95）、kit に切り出す前後のアプリ側の通信まわりのコード量
