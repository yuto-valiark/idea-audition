## 1. 何を証明したいのか：2種類の実験

これまで考えていた CAMP のベンチマークは「技術として優れているか」を示すもの。
IDEA AUDITION で本当に示したいのは「**人間とAIが一緒に議論すると、会議の質が上がるのか**」。

| 実験 | 問い | 主な指標 |
|---|---|---|
| CAMP の技術評価 | 人間とAIの協調処理を、どれだけ安全・簡潔に実装できたか | コード削減率・競合の発生と解決・再接続の成功率・古いAI結果の破棄 |
| IDEA AUDITION の体験評価 | 人間とAIが影響し合いながら、納得できる結論を出せたか | 対話の成立数・意見の反映率・意思決定の質 |

### 「AIを使った会議」と「AIと協働した会議」は違う
- AIが10案出して人間が1つ選ぶだけ → 提案支援に近い（一方通行）
- 人間が問題を指摘 → AIが改善 → 別の人間が反論 → AIがさらに調整 → **相互作用が成立している**

この違いを測りたい。「AIとのやり取りが多い＝良い会議」とは限らないので、量と質を分けて評価する。

## 2. 測る指標（6つ）

| 指標 | 測り方 | 分かること |
|---|---|---|
| 対話往復数 | 人間の指摘 → AIの応答 → 人間の再評価、が成立した回数 | 一方通行で終わっていないか |
| 意見反映率 | 人間の具体的な要望のうち、AIの次の案に反映された割合 | AIが人間の意図を取り込んだか |
| 参加の均等さ | 4人の発言・判断の分布 | 一部の人だけで決めていないか |
| 対立の解消率 | はっきりした対立のうち、合意か理由つきの決定に至った割合 | 対話が意思決定につながったか |
| 企画の改善幅 | 最初の案と最後の案を、第三者が案の出どころを伏せて評価 | 対話で企画が良くなったか |
| 納得度 | 終了後に各参加者が7段階で回答 | 結論を受け入れられたか |

特に重要なのは **意見反映率・企画の改善幅・納得度** の3つ。会議が盛り上がっただけでなく、良い結論に近づいたかを示せるため。

## 3. 「人間とAIの対話」をイベントの因果関係として記録する

チャットログをそのまま保存するのではなく、**どの人間の判断が、どのAIの提案に影響したか**を記録する。

対話が成立した1サイクルの例（架空）：

1. 人間A（指摘）「このサービス、学生には価格が高すぎる」
2. AI（改善）「月額料金を下げ、無料プランを追加します」
3. 人間B（再評価）「無料プランなら使いやすそう。収益モデルは？」
4. AI（再提案）「法人向け有料プランで収益化します」

記録の形の案：

```ts
type DialogueEvent = {
  eventId: string;
  sessionId: string;
  actorType: 'human' | 'agent';
  actorId: string;
  action: 'feedback' | 'proposal' | 'revision' | 'evaluation';
  parentEventIds: string[]; // 何に応えたか
  timestamp: number;
};
```

注意：**イベントがつながっていることと、実際に意見が反映されたことは別**。反映されたかどうかは、変更前後の案を人間が評価するか、独立した評価モデルで判定して確かめる必要がある。

## 4. 比較実験（3条件）

| 条件 | 内容 |
|---|---|
| A：人間だけ | 4人でアイデアを出し、議論して1つに絞る。AIは使わない |
| B：ふつうのAI支援 | 4人が一般的なチャットAIを使いながら議論して1つに絞る |
| C：IDEA AUDITION | 4人と複数のAIキャラが、選抜・改善・再評価を繰り返す |

- 同じテーマの難しさ・制限時間・人数・同程度のAIモデルにそろえ、テーマと実施順を入れ替える
- **B と C の比較が最重要**。ここで差が出れば「AIが優秀だった」ではなく「IDEA AUDITION の会議体験に価値があった」と言いやすい
- 差が出なければ「対話は増えたが、品質向上は確認できなかった」とそのまま報告する。それも結果として価値がある

### ハッカソン期間中の現実的な規模
- 4人×3チーム程度の予備実験。各チームが B と C を別のテーマで体験し、順序を入れ替える
- 1回15分。終了後に全員が納得度・参加感・AIとの協働感を回答
- 最初の案と最後の案を匿名化して、第三者が「実現可能性」「独自性」「課題解決力」で採点
- この規模では一般化できる結論は出せないが、プロトタイプの有効性の検証としては意味がある

## 5. 体験としての見せ方

「会議中に人間の意見が何回AIに反映され、その結果、企画がどう変わったか」をリアルタイムに表示する。
会議の最後に「**あなたたちの判断で、AIのアイデアがこう進化しました**」と見せる。実験用のログで終わらせず、体験価値そのものにする。

> CAMP で協働を成立させ、IDEA AUDITION で協働の成果を見えるようにする。この2層をそれぞれ実験で示す。

## 6. ロゴ

- OSS にもロゴは普通にある（Docker、Kubernetes、React など）。README・ドキュメント・npm・登壇資料で使う
- IDEA AUDITION（紫のネオンとキャラが主役）とは別ブランドにして、シンプルで洗練されたものにする

## 7. プロトコルと OSS の関係

| | プロトコル | OSS |
|---|---|---|
| 正体 | 通信と振る舞いの仕様 | 公開されたソフトウェア |
| 目的 | 違うシステム同士が正しく協調できるようにする | 他の開発者が使い、改良できるようにする |
| 成果物 | 仕様書・メッセージ定義・状態遷移の規則 | ソースコード・ライセンス・README |
| CAMP では | [CAMP v1 仕様](../protocol/camp-v1.md) | `@camp-protocol/kit`（クライアントとサーバーの実装）＋適合テスト |
| 公開は必須か | いいえ | はい（OSS ライセンスで公開する） |

- プロトコルを設計しただけでは OSS にならない。OSS のために独自プロトコルが必要なわけでもない。CAMP はその両方を自分たちで作っている
- 例：HTTP はプロトコル、React は OSS ライブラリ。CAMP は名前をプロトコルとプロジェクトの両方に使う
- ライセンスを付けずに GitHub に置いただけでは、自由に使える OSS とは扱われない。MIT なら商用利用・改変・再配布ができる
- 一言でいうと：**CAMP プロトコル**＝人間とAIがリアルタイムに協調するための共通ルール／**CAMP OSS**＝そのルールを誰でもアプリに組み込める実装／**IDEA AUDITION**＝CAMP を使う最初のアプリ

### クライアントとサーバーの役割
- **クライアント**（アプリ側で使う）：接続・コマンド送信・イベント受信・状態の同期・再接続。アプリは「何をしたいか」を呼ぶだけでよい
- **サーバー**（ルールを実行する側）：コマンドの検証（重複・権限・競合）、会議ごとに直列化して順序を確定、古いAI結果の拒否、確定した変更を全員に配信
- 「決勝は最大3体」「昇格できるのは審査員だけ」といった**業務ルールはアプリ側**が書き、CAMP はそれを競合なく実行する土台を提供する
- 一言で：クライアントは「参加者の意図を届ける」、サーバーは「複数の意図とAIの結果を調停し、確定した状態を共有する」

### 壁打ちの内容と、実際の実装との違い
壁打ちで出た API 例は「設計のイメージ」だった。実装済みの `@camp-protocol/kit` とは次の点が違う。

| 壁打ちでの案 | 実際の実装 |
|---|---|
| `protocol` / `client` / `server` の3パッケージ | 1パッケージ＋入口を3つに分割（`@camp-protocol/kit`、`/client`、`/server`）。バージョンを1つにそろえられる。クライアントが `ws` や `node:*` を読み込まないことは境界テストで保証済み |
| `camp.command(type, payload)` が revision を自動で付ける | `client.send(type, payload, { expected })`。どの版を前提にするかはアプリが明示する |
| `server.registerCommand(type, handler)` | `CampRoom` に `commands: { TYPE: (room, payload, ctx) => … }` を渡して業務ルールを書き、`room.reject` / `room.emit` / `room.task` を使う |
| Cloud Run の複数台では1プロセスのキューでは整合しない | 本番は `--max-instances 1`＋セッションアフィニティで1台に固定している。複数台にするなら、部屋ごとの担当サーバーを決める仕組みが別に要る |

## 8. CAMP はどこが新しいのか（言い方の注意）

| 技術 | 主に解決する問題 |
|---|---|
| WebSocket | 双方向通信 |
| Socket.IO | リアルタイムのイベント配信・再接続 |
| Yjs | 複数人の共同編集とデータ同期 |
| MCP | AIとツール・データの接続 |
| A2A | AIエージェント同士の連携 |
| **CAMP** | **人間とAIの操作・判断・非同期処理を、共有セッションの上で調停する** |

- 正確な言い方：「世の中にない技術要素を発明した」ではなく、「**これまでアプリごとに個別に書いていた協調処理を、1つのプロトコルとして標準化した**」ことが新しい
- `expected.rev` による競合検出や epoch による古いAI結果の破棄は、単体では既知の手法
- 網羅的な先行技術調査はしていないので「世界初」とは言わない

独自性が出そうな3つ：

1. **Human-AI Causal Consistency**：AIが生成を始めた時点と結果が返った時点で人間の判断が変わっていたら、結果を採用・破棄・再生成のどれにするか判定する（epoch で一部実装済み）
2. **Intent Arbitration**：複数人の同時操作を、先着順だけでなく、意図が両立するかやアプリが決めた優先規則で調停する（未実装）
3. **Decision Provenance**：人間の指摘 → AIの改善 → 再評価 → 最終決定、の因果を追えるようにする（**この計画で実装する**）

カテゴリとしての位置づけ：

> **CAMP — Collaborative Agent Mediation Protocol**
> A shared decision layer for humans and AI agents.

最後に一番大事なこと：**「CAMP という名前を付けた」ことではなく、「CAMP という共通仕様を作ったことで、これまでアプリごとに解いていた問題を実際に減らせた」ことがすごい**。そこを実測値で示す。
